# ERP 员工历史问题 → V2 正式需求

> 来源：`ERP历史问题总结.xlsx`，2026-07-24 读取。该文件是员工真实使用反馈，不等同于最终技术方案；V2 应解决问题本身，同时避免复制旧系统的权限和数据质量缺陷。

## 总体结论

员工反馈集中在四个根因：

1. 订单录入缺少明确的成功反馈和稳定业务编号，售前与售后对单困难。
2. 地址、电话、SKU、币种等主数据缺少自动校验，错误被推迟到售后和发货阶段处理。
3. 图片、导入导出等高频操作性能差或字段不完整，造成重复劳动。
4. 物流提醒没有按业务阶段分级，售后被大量普通更新干扰，真正重要的派送更新反而不突出。

## 1. 订单编号与售前可见范围

员工需要：保存后明确显示订单号；可以查看自己当月订单总记录，但不能查看物流状态；允许录入外部/店铺单号，后续发货和跟单保持对应。

V2 要求：

- 保存成功后显示订单号、客户、商品和保存时间，并提供“继续录单 / 查看订单”。
- 业务订单号采用数据库唯一序列，格式通过配置管理，例如 `{业务前缀}{日期}-{当日序号}`，不能依赖随机数。
- 外部/店铺订单号与系统订单主键分离，并按业务板块配置唯一或重复预警规则。
- 售前默认只能查询自己 Membership 创建的订单和月度统计。
- 物流状态、轨迹、售后备注等字段通过字段级权限隐藏；API 同样不得返回。
- 发货和售后引用同一订单，不允许为了转单覆盖原订单号。

验收：并发录单不重复；保存结果明确；售前能看本人月度数量但无法从 API 得到无权查看的物流字段。

## 2. 地址识别与校验

员工需要：详细地址自动识别省、市；希腊、意大利使用物流商地址库；避免售前和发货重复核对。

V2 要求：

- 地址执行标准化、国家识别、邮编校验、省/州、城市和详细地址拆分。
- 自动结果必须由员工确认，保存原始地址和结构化地址。
- 国家规则、邮编格式和物流商地址库版本化配置。
- 物流商 WPS/Excel 地址库先导入隔离主数据，经校验后使用。
- 不使用维基百科作为正式地址校验源，选择稳定且有服务协议的数据源。

验收：希腊、意大利样例可匹配；无法确认的地址进入人工确认；发货端复用已确认地址。

## 3. 聊天截图与订单附件

员工问题：一张图片上传需要一至两分钟。

V2 要求：

- 浏览器先压缩并即时预览，然后并行上传。
- 使用独立附件记录，不固定为 `image_1...image_8`。
- 显示单图进度、成功、失败和重试；部分失败不阻塞全部图片。
- 限制类型、大小、数量并进行安全校验。
- 订单可先保存草稿，附件后台继续上传；正式提交前检查必要附件。

验收：选择后立即预览；多图并行；单张失败可重试且不会丢订单或重复建单。

## 4. 派送阶段提醒优先级

员工需要：派送中每 30 或 60 分钟刷新；派送后的任何新信息最高优先级；派送前除“三个工作日未更新”外不提醒普通更新。

V2 要求：

- 所有已发货订单进入跟单售后工作台并持续同步。
- 普通运输更新只更新轨迹，不产生售后通知。
- 运输阶段超过可配置工作日阈值未更新才进入“需关注”。
- 派送阶段提高同步频率，每个新事件进入高优先级变化队列。
- 派送失败、地址问题、联系不上、拒收、退回生成必须处理的售后任务。
- 来源事件用幂等键去重；同步由后台任务执行，不由浏览器页面重复触发。
- 同步频率、工作日历和优先级规则配置化。

验收：正常运输可见但不产生普通提醒；派送新事件及时进入高优先级；三个工作日正确排除周末/节假日；重复同步不重复提醒。

## 5. 国家与物流专线筛选

员工需要：按目的国家筛选；PT、ES 为西葡专线；GR、HR、CK、PL、SK、IT 为东欧专线。

V2 要求：

- 国家、物流渠道、专线和服务区域全部数据库驱动。
- 一个专线关联多个 ISO 国家代码，修改映射无需改代码。
- 支持国家、专线、物流商和状态组合筛选。
- 创始人已于 2026-07-24 确认：员工反馈中的 `CK` 指捷克，V2 统一使用 ISO 国家代码 `CZ`。
- 导入文件出现历史值 `CK` 时转换为 `CZ`，同时保存原始输入和转换记录，不能静默丢失来源。

验收：后台修改映射后筛选和导出立即使用新配置；未知代码不自动归线。

## 6. 申报金额与币种

员工需要：申报金额可选择目的国家货币，不能固定人民币。

V2 要求：

- 申报金额、COD 金额和订单售价分别保存金额及 ISO 4217 币种。
- 默认币种由订单模板/目的国家带出，授权人员可修改。
- 金额使用最小货币单位或 Decimal，禁止 JS 浮点作为资金事实。
- 物流商或海关模板可以配置申报币种，不把“目的国家币种”写死为唯一规则。

验收：欧元等币种正确保存、显示、导出；模板变更不影响历史订单。

## 7. 商品型号、颜色和电话号码

员工需要：订单填写型号与颜色；WhatsApp/电话带正确国家区号；杜绝空格、缺少 `+`、多余本地前导零等错误。

V2 要求：

- 型号和颜色来自 SKU 属性，不作为互不关联的重复自由文本。
- 同时保存原始号码和标准 E.164 号码。
- 根据订单国家提示区号，允许粘贴空格/短横线并给出标准化建议。
- 本地前导零、缺少 `+` 等情况必须由员工确认修正。
- 号码长度按国家规则校验，不能写死“全部九位”。
- WhatsApp 与主要电话可相同或独立，分别校验。

验收：`+48...`、`48...` 和含空格号码可解析；明显错误不能正式提交；售后能看到标准号码并追溯原始输入。

## 8. 导出字段完整性

员工需要：导出包含现有字段、标记信息和售前下单信息。

V2 要求：

- 导出模板数据库驱动，按渠道/专线配置字段、顺序、标题和格式。
- 售前原始字段、确认后的标准字段、跟单标记分栏导出，不能互相覆盖。
- 导出使用独立权限并应用字段级脱敏。
- 记录模板版本、筛选条件、操作者、时间和文件校验信息。

验收：对应模板字段端到端不丢失；无权限用户无法通过导出获取电话、地址、金额或物流信息。

## 9. 物流转单号与包裹目的地

员工需要：填写物流转单号用于转寄；可修改包裹发送目的地。

V2 要求：

- 不把“收件人”字段改名或覆盖为转单号。
- `Shipment` 支持一单多运输段；每段有承运商、物流单号、起点、目的地和轨迹。
- 主物流单号和末端转单号通过运输段关联，保留完整历史。
- 修改目的地需要独立权限、原因、变更前后快照和审计。
- 已发货后不覆盖订单原地址，使用改址请求或新运输段。

验收：主单可追溯全部转单号和轨迹；改址保留原地址与审计；无权限员工不能修改目的地。

## 开发优先级

### P0

1. 发货后自动进入跟单售后工作台。
2. 全物流跟踪、派送最高优先级、三工作日未更新规则。
3. 稳定订单号、成功反馈和售前字段级可见范围。
4. 电话标准化、SKU 属性和金额币种正确性。
5. 物流转单采用多运输段模型，禁止覆盖原字段。

### P1

1. 地址解析与物流商地址库。
2. 高性能附件上传。
3. 国家/专线配置与筛选。
4. 完整可配置导出。

## 需要创始人确认

- 订单号展示格式、业务前缀以及每日序号是否按北京时间重置。
- 希腊、意大利物流商地址库样本和允许使用的版本。
- 派送阶段同步周期固定 30 分钟，还是按渠道分别配置。
