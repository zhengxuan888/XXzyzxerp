# 财务：物流商结算、COD 回款与付款核销实施计划

## 结论

旧 ERP 的“物流回款、COD 回款账单、对账管理、付款记录”都应归入**财务板块**。物流运营只负责导出订单、回传运单号、确认发货和追踪；它不应拥有供应商账单、回款金额或付款核销的写入权限。

本计划是下一开发批次的最小边界，不连接银行、支付渠道、物流商或旧生产数据。

## 旧 ERP 能力的保留与整合

| 旧功能 | V2 归属 | V2 改进 |
| --- | --- | --- |
| 物流回款 / 物流账单 | 财务：供应商结算单 | 去掉重复页面，统一账单、导入批次、证据、审核与分页 |
| COD 回款账单 | 财务：COD 结算单 | 账单行与订单/运单可追溯匹配，不直接改订单金额 |
| 账单导入 | 财务：账单导入批次 | 先预检、逐行错误、文件哈希、版本化映射、确认导入 |
| 对账管理 | 财务：对账异常工作台 | 明确已匹配、差异、未匹配、已忽略、待复核状态 |
| 付款记录 | 财务：付款与核销 | 付款必须分配到具体结算单/账单行，不是自由填写的费用 |

## V2 最小模型

所有业务事实都包含 `legal_entity_id`、`business_unit_id`，需要时包含 `department_id`，并使用全新 V2 ID。

1. `finance_counterparties`
   - 物流商、仓储商或其他结算对象；编码、名称、类型、启停、付款资料引用（不存明文 Secret）。
2. `finance_statement_templates`
   - 可配置账单模板、导入列映射、表头扫描行数、币种/金额字段策略、版本和启停。
3. `finance_statement_import_batches`
   - 原始文件、SHA-256、模板版本、预检状态、导入人、时间和审计。
4. `finance_statements`
   - 供应商账单或 COD 结算单；期间、原币种、金额、状态、证据、审批关联。
5. `finance_statement_lines`
   - 单号/订单号/运单号、金额分项、来源行、匹配状态、例外原因；金额用最小货币单位 `BIGINT`。
6. `finance_reconciliations`
   - 账单行与订单/运单的匹配、差异、证据、复核人和处理结果。
7. `finance_payments` 与 `finance_payment_allocations`
   - 付款事实及其对结算单/账单行的核销，不允许用浮点数或静默改账。

## 状态机

```text
上传账单 → PREVIEWED → IMPORTED → RECONCILING
                                   ├─ 差异待处理 → EXCEPTION
                                   └─ 全部确认 → APPROVED → PAID / PARTIALLY_PAID
                                                            → VOID（只允许审计化作废）
```

- 导入预检与确认必须是两个阶段；确认只能使用同一批次、同一文件哈希、同一模板版本的预检快照。
- 手工匹配、差异忽略、审批、付款、核销、撤销均需原因和 Audit Log。
- 不能物理删除已导入账单、对账或付款事实。

## 动态权限

建议稳定 Action key（角色与菜单映射仍由数据库配置）：

- `finance.counterparty.read/manage`
- `finance.statement_template.read/manage`
- `finance.statement.read/create/import.preview/import.confirm/approve/void`
- `finance.reconciliation.read/manage/resolve`
- `finance.payment.read/create/approve/void`
- `finance.pii.read`

服务端必须基于当前 Membership + Action + Scope 再计算可读取或写入的公司、业务板块、部门与站点。物流人员默认只能读到与其订单有关的结算状态摘要；财务金额、银行资料和完整对账明细需要单独 Action。

## 页面与日常操作

1. **财务工作台**：待预检、待确认、对账差异、待审批、待付款、临近付款日卡片；卡片和快捷入口可配置。
2. **物流商结算单**：列表、期间/对象/币种/状态筛选、稳定分页、导入、预检、确认和原文件下载。
3. **COD 回款与对账**：按账单批次查看匹配率、未匹配订单、金额差异、人工处理原因和证据。
4. **付款与核销**：创建付款草稿、提交审批、确认付款、分配核销、剩余余额和作废审计。

## 实施顺序

1. 先建立模型、权限、动态菜单与只读列表；
2. 完成账单模板 + Excel 预检 + 批次确认；
3. 完成订单/运单安全匹配与差异工作台；
4. 完成审批、付款与核销；
5. 最后再接入真实物流商账单格式、银行或支付渠道（另行授权）。

## 测试 Gate

- 无 Membership、跨业务板块、跨部门、直链详情、撤销/到期 Grant 均拒绝。
- 模板、对象、币种、列映射、新物流商无需修改代码。
- 同一个账单文件重复上传幂等；重复确认不生成重复账单行或付款。
- 科学计数法、前导零、空金额、未知订单/运单、跨板块数据、币种不一致均进入预检异常，不能静默导入。
- `BIGINT` 最小货币单位端到端保持精度；不允许 JS `float/double` 作为账务事实。
- 付款金额不能超过已批准且未核销余额；作废只能生成审计化反向记录。
- 列表统一分页、稳定排序、筛选、空状态、错误状态和导入错误下载。

## 需要业务确认的边界

1. 每家物流商的正式账单样表、计费项目和原始币种；
2. COD 回款是否按订单、运单、批次或账期为唯一匹配键；
3. 汇率来源、换汇日期、允许差异和人工容差；
4. 哪些岗位可以提交、复核、批准、付款和查看银行/客户隐私字段；
5. 银行流水、支付凭证和真实接口的接入授权。
